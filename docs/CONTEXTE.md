# FITNESS ROYALE — Contexte du projet

> Fichier de référence à garder dans le projet Claude. Il résume toute l'application : vision, barème, fonctionnalités, plan. À mettre à jour au fil du projet.

---

## 1. En une phrase

**Fitness Royale** = une application de fitness compétitive, dans l'esprit *Clash Royale mais dans la vraie vie*. Tes performances réelles en salle te font monter des paliers, tu rejoins un clan lié à ta salle, et tu te compares à tes amis et au monde entier.

Marque / univers : **Club SP** — slogan « FIGHT FOR IT ».

---

## 2. Le système de paliers (cœur du jeu)

### Les paliers
- **Hommes (6 paliers)** : Bronze → Silver → Gold → Legend → Titan → **Royal**
- **Femmes (5 paliers)** : Bronze → Silver → Gold → Legend → Titan

*(Note : le palier « Royal » remplace l'ancien nom « Olympe », pour coller au nom Fitness Royale.)*

### Deux classements complémentaires
1. **Palier par exercice / relatif** — basé sur le barème Club SP ci-dessous : pour chaque exercice, la performance donne un palier.
2. **Palier global** — la moyenne des paliers obtenus sur les exercices, pour situer chaque membre d'un seul coup d'œil.

## 3. Fonctionnalités de l'application

- **Paliers & avatar évolutif** — l'apparence de l'avatar change à chaque palier franchi (physique, équipement, aura, décor). L'avatar = statut et fierté.
- **Deux classements** — par exercice/relatif + palier global. Classements entre amis, par salle, par pays, mondial. Saisons façon Clash Royale.
- **Clans par salle** — chaque salle de gym = un clan. Classement des clans (quelle salle est la plus forte ?).
- **Chat** — chat de clan + messages entre amis. Transforme le tracking en communauté vivante.
- **Compétitions (duels)** — affrontements directs. Format de base : charge fixe imposée, **le plus de répétitions gagne**. Variantes : charge relative, charge absolue, défi de clan, **mode Royale** (multijoueur, un seul en tête). Noms envisagés : Duel / Battle / Arène / Clash / Royale.
- **Conseils fitness** — programmes et conseils adaptés au palier de chacun.

## 4. Le problème clé : la preuve de performance

Pour que le classement soit crédible, il faut prouver qu'une perf est réelle. Approche retenue pour démarrer :

- **Trois statuts de perf** : *Déclaré* (auto-reporté, suivi perso uniquement) · *Vérifié communauté* (vidéo validée, compte au classement) · *Vérifié salle* (validé par une salle partenaire, badge officiel).
- **Vidéo** pour valider une perf classée ; validation par la communauté au début, IA d'analyse vidéo plus tard.
- **Salles partenaires** comme points de confiance.
- Le classement officiel n'utilise que le vérifié.

## 5. Plan & rythme

- **Rythme** : ~1h par jour. **Horizon** : ~6 mois jusqu'au lancement de l'app.
- **Phase 0 (Semaine 1)** : concept figé + prototype de calcul + **lancement de la communauté** (avant l'app).
- **Phase 1 (S2-3)** : animer la communauté, collecter de vraies perfs, calibrer le barème.
- **Phase 2 (S4-8)** : coder toute la logique en Python + mini web app.
- **Phase 3 (S9-14)** : back-end (FastAPI) + base de données, comptes, classements, clans, upload vidéo.
- **Phase 4 (S15-22)** : app mobile (MVP), beta fermée avec la communauté.
- **Phase 5 (S23-26)** : compétitions, corrections, mise sur les stores, **lancement public**.

Principe : la communauté vit **dès la semaine 1**, bien avant l'app. Fini vaut mieux que parfait (on lance un MVP, on améliore après).

---

## 6. Approche technique

- **3 briques** : app (front-end mobile) · serveur (back-end, le « cerveau ») · base de données (la mémoire).
- **Back-end en Python** (FastAPI) — toute la logique (paliers, duels, classements). Base : SQLite en proto, PostgreSQL ensuite.
- **App mobile** : Flutter ou React Native (un code → iOS + Android). Web app intermédiaire possible (Streamlit) pour tester vite.
- Le créateur est **débutant en Python** : on commence par la logique en Python, l'app mobile vient plus tard.
